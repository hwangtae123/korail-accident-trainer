# 작업 목록 (리드가 이걸 기준으로 Task를 만든다)

Task 제목은 `[BE] BE-1 근거 자동 확인`처럼 접두어 + ID로 만든다. 완료 표시할 때 품질 게이트가 돈다.
필요 없는 항목은 지우거나 순서를 바꿔도 된다.

## 백엔드 (backend-dev)

**BE-1 근거 자동 확인**
- 구조화 직후 모든 `Evidence`에 대해 `quote`를 해당 `page`의 파싱 텍스트(`parsed.json`의 pages)에서 찾아 `verified`를 채운다. 공백·줄바꿈 차이는 무시. `quote`나 `page`가 비면 `null`.
- LLM이 `verified`를 채워 보내도 무시하고 코드 결과로 덮어쓴다.
- 수용: 맞는 구절 true, 없는 구절 false, 빈 구절 null인 테스트. 기존 테스트 통과.

**BE-2 시나리오 저장 API (`PUT /api/reports/{id}/scenario`)**
- 계약 형식 그대로. `answer_id`가 그 단계 options의 id 중 하나가 아니면 422. 저장 시 `review_status`는 "검수 전"으로.
- 수용: 정상 저장, 잘못된 answer_id 422, 없는 보고서 404, 저장 후 GET에 반영되는 테스트.

**BE-3 작업 전 브리핑 API (`POST /api/briefing`)**
- `work`로 검색 → 비슷한 사고 3건 → 그 보고서들의 안전권고·기여요인만 LLM에 주고 `summary`와 `checklist`를 만든다.
- checklist 항목의 `source_report_id`는 검색된 보고서 중 하나여야 한다(코드로 검증해서 아니면 버림). evidence는 원래 항목의 것을 그대로 쓴다.
- 수용: stub LLM으로 형식·출처 검증 테스트, 보고서 0건일 때 빈 결과(200).

**BE-4 (선택) 규정 이름 맞추기**
- `shared_rules` 비교 때 "선로유지관리지침"과 "선로 유지관리 지침", 약칭 등을 같은 규정으로 보도록 정규화 사전(`app/rule_aliases.py`)을 둔다.
- 수용: 표기만 다른 두 규정이 shared로 잡히는 테스트.

## 프론트 (frontend-dev)

- **FE-1** 레이아웃 + 보고서 목록 + PDF 업로드(여러 개) + 처리 상태 폴링(3초) + 상태 태그. `new:false`면 "이미 있는 보고서" 안내 후 그 보고서 열기.
- **FE-2** 사고 정보 탭: 섹션 전부 + p.N 링크 + verified 표시 + "비슷한 과거 사고" 카드 + 공통점 요약.
- **FE-3** 판단 훈련 탭: 시작 → 단계 → 결과, 검수 완료 표시, 다시 생성(확인창 후 상태 폴링).
- **FE-4** 시나리오 편집 화면 (BE-2 전에는 저장 버튼 막고 "준비 중").
- **FE-5** 유사사고 검색 + LLM 요약.
- **FE-6** 작업 전 브리핑 화면 + 인쇄용 레이아웃 (BE-3 전에는 "준비 중").
- **FE-7** 반복 패턴 화면.

의존: FE-4 저장 동작 확인은 BE-2 이후, FE-6 결과 확인은 BE-3 이후. 화면은 먼저 만들어도 된다.
